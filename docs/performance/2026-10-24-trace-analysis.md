# 2026-10-24 场景性能记录分析

分析对象：`Trace-20261024T193618.json.gz`。以下先记录原始性能分析，再补充根据分析实施的代码优化。本轮未启动浏览器或执行视觉验证；优化收益仍需新 trace 对照确认。

> 历史快照说明：本报告记录 2026-10-24 当时的渲染实现。2026-10-27 起，地坪改为直接显示已带透视的完整 PNG；本节 Mesh 路径描述不代表当前代码。

## 结论

这次卡顿主要表现为绘制提交之后的合成、GPU 进程等待和显示延迟。主线程业务计算没有占满帧预算。

可以确认主线程空闲很多、动画回调短，而帧到达显示端很慢；不能凭这份记录确定某个着色器的真实 GPU 执行时间，也不能排除驱动、硬件加速状态、其他页面共享 GPU 或录制环境的影响。优先减少明确存在的离屏滤镜与像素负载，并逐项对照测量。

| 项目 | 改动 | 预期影响与边界 |

## 记录范围与实测

- 可见录制窗口 4.533507 秒，10,843 个原始事件。
- 页面为 Vite 开发服务；记录元数据显示 Pixel 10 设备模拟、宿主 DPR 为 2。这不是 Pixel 10 真机性能结果。
- 窗口内有 30 轮主线程动画更新，约 6.6 轮/秒；相邻更新平均间隔 143.06ms，最大 545.16ms。这里是动画更新频率，不能与最终完整画面呈现帧率混为一谈。

| 动画回调函数 | 90 次，总计 100.35ms | 多个回调属于同一轮动画，不能把 90 次当作 90 帧 |

| 主线程 CPU 采样 | 约 89.9% 为 `(idle)` | 与脚本并未持续阻塞主线程相符 |
| 合成帧接收到开始绘制 | 平均 153.69ms | 等待明显 |

异步帧阶段会跨帧并行，且部分属于同一帧的不同分支；各阶段不能累加为总耗时。原始记录中也有 `BACKFILL` 与 `FORKED`，不直接用 DroppedFrame 事件数量计算掉帧率。

共享 GPU 进程主线程的完整 RunTask 墙钟时间累计约 4.36 秒，对应线程 CPU 时间约 0.43 秒。大量时间没有转化为线程 CPU 运算，支持存在等待或背压的判断；GPU 进程还包含其他 renderer 的任务，不能全部归因于本页面。

本段没有资源加载事件，不能用于判断首屏下载、图片解码和初始化资产生成速度。

## 代码中最值得优先处理的开销

### 1. 左右前景：视觉极弱的模糊仍然启用实时滤镜

- `src/pixi/scene/components/registry.ts:111`：`FOREGROUND_BLUR_STRENGTH = 0.15`。
- `src/pixi/layers/SceneThemeLayer.ts:208`：只要强度大于 0，便创建 `BlurFilter`，`quality: 2`。

极低强度不等于没有滤镜成本。两侧前景都可能进入离屏绘制、模糊处理和结果合成。CPU 采样也出现了 Pixi 的滤镜调用路径，但不能把这条路径的 CPU 时间当作 GPU 时间。

建议首先对照关闭这两处弱模糊；若确实需要景深，优先使用已带柔焦的素材，或者只在素材变化时生成缓存。不要仅把强度从 0.15 降为 0.1，因为滤镜仍然存在。

### 2. 地板：日间颜色不变，仍保留调色滤镜

- `src/pixi/layers/FloorLayer.ts:460`：地面 Mesh 始终绑定 `ColorMatrixFilter`。
- `src/pixi/layers/FloorLayer.ts:477`：主题地板在开灯、日间模式直接返回，矩阵保持单位矩阵。

这意味着日间效果不需要改变颜色，滤镜对象却仍挂在渲染节点上。现已在该模式下移除滤镜，日落、夜间仍使用原滤镜；设计上不改变日间像素颜色。

### 3. 内部渲染分辨率与抗锯齿

- `src/pixi/engine/PixiStage.ts:46`：分辨率最高为 DPR 2。
- 同文件第 48 行开启 `antialias`。

同一逻辑画幅在 DPR 2 时需要处理约 4 倍于 DPR 1 的像素；滤镜与大范围半透明覆盖又会重复处理这些区域。

建议把 DPR 2 与 1.5 单独对照：后者理论像素量减少 43.75%，但不能承诺帧率按比例增加。通过用户视觉反馈确认遗像、文字和木纹是否可接受，再决定是否按设备能力自适应。抗锯齿应另做一项对照，避免同时改变两个变量。

### 4. 大范围透明光效与玻璃背景

- `GodRaysLayer` 使用多个较大范围的加色精灵。
- `SceneThemeLayer` 的灯光和前景、`MemorialPortraitLayer` 的光环会持续合成。
- 底栏等 DOM 控件使用 `backdrop-blur-*`，背景画布持续变化时值得对照检查合成成本。

这些是候选负担，不是本记录已量化到毫秒的独立热点。建议先逐组关闭光效、前景和 DOM 背景模糊测收益，再确定是否减少透明留白、缩小覆盖范围或改用预处理素材。单纯降低 alpha 通常不会消除绘制调用与透明区域处理。

### 5. 供桌阴影与点光源模糊

- `src/pixi/layers/AltarTableLayer.ts:100`、`:142`：阴影和点光源各有 `quality: 3` 的模糊滤镜。
- `setCandleLights` 已有参数缓存，不能说它无条件每帧重建光照几何。
- `getCandleInfluence` 在日间返回 0，因此不能直接把夜间烛光绘制成本归因到当前录制。

现已在日间隐藏无贡献的环境压暗与点光 Graphics，并将阴影、点光 BlurFilter 的质量从 3 调为 2。夜间模糊的收益仍需单独测量；是否改为渐变纹理应先核对画质与滤镜范围。

## 次优先：业务计算和动态贴图

CPU 采样中，Pixi render 路径累计约 39.5ms，场景 Ticker 回调约 11.5ms，PropsLayer.update 约 7.5ms，烟雾 update 约 5.2ms，世界时钟 tick 约 6.7ms。这些是包含子调用的采样估算，不能彼此相加。

- `PropsLayer.ts:600` 已对烛火与香烟贴图按 delta 累积降频，目标约 30FPS；不要重复实现一遍同样的降频。
- 烛火、烟雾仍使用 Canvas 重绘并更新纹理。可以进一步避免隐藏或完全熄灭后的无效上传，缓存不变的渐变/几何，但本次 CPU 数据不支持优先重写整个烟火系统。
- 世界时钟逐帧克隆生命周期数据，可以改为较低频率推进，并按真实经过时间累计；当前耗时很小，应晚于 GPU 负载优化。
- 多个 `_tick` 回调不等于重复绘制整张场景；需区分 Pixi 应用 Ticker 和事件系统 Ticker，不能仅凭回调数删除。
- 不建议把所有 PNG 精灵一律 `cacheAsTexture`。简单精灵本身可批处理，缓存可能增加离屏纹理与内存，需验证收益后采用。

## 性能面板本身的误导

`src/ui/space/controls/FpsMonitor.tsx:159` 开始的“当前页面主要性能开销瓶颈”是写死的文案，不是检测结果。

其中写着“80+ 尘埃每帧 shadowBlur”“双蜡烛与香炉并发 4 个独立 RAF”“全屏 SVG 模糊”。当前代码的浮尘实际为 Sprite，池上限 18；烟火由场景 Ticker 驱动；光束也是纹理精灵。这些旧文案会误导优化方向。

此外，该面板显示的 frameTime 来自相邻 RAF 时间差，衡量更新间隔，并不是单帧 JS 或 GPU 真正执行耗时。现已明确标注“帧间隔”，删除固定原因说明并写明此监控范围；P95 帧时间和长帧计数仍可作为后续增强项。

## 后续对照建议

1. 基线：同一设备、同一场景、相同日照与供品，页面稳定后录 10–15 秒；优先用生产预览减少开发环境干扰。确认硬件加速状态，控制其他活动页面负载。
2. 对照新旧 trace 的动画更新间隔、主线程工作、提交到呈现延迟；这些改动尚未建立量化前后结论。
3. 由用户在 iPhone 与 iPad 上检查 DPR 1.5 的遗像、文字、框架和木纹清晰度；若不够清晰，按设备分别调整上限，再复测。
4. 日间与夜间分别检查供桌模糊效果和地板色彩矩阵是否按预期启用。

每次比较平均动画更新频率、P95 帧间隔、提交到呈现延迟，并由用户确认视觉效果。当前记录不支持承诺优化后能到达某个固定帧率。
